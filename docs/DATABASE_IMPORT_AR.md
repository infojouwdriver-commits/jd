# تحويل نسخة Zoer إلى PostgreSQL للاختبار

اعتمد المشروع مسار PostgreSQL مستقل؛ اقرأ INDEPENDENT_DATABASE_AR.md لقواعد العقد والتدقيق وقبول القيود. استرجاع مخطط Zoer يبقى خياراً إذا أردنا مطابقة نظامه، وليس شرطاً لبناء النظام المستقل.

## استخراج المخطط الحي عند طلب مطابقة Zoer

دخلنا مشروع Zoer وجلبنا ملفات SQL الأصلية في V299، ثم تحققنا من V300: جميع الملفات الـ302 مطابقة، ولم يُنشأ ملف مخطط حي. هذه المصادر تحتوي تاريخ تعديلات وبذور بيانات؛ لا تنفذ `app.sql` أو `database-migration.sql` على الإنتاج، ولا ترفع النسخة الخاصة إلى GitHub. ما زالت البنية المستنتجة أدناه غير معتمدة كمطابقة لقاعدة Zoer الحية.

عند توفر اتصال PostgreSQL مصرح للقراءة، تستخرج الأداة التالية DDL من القاعدة نفسها بواسطة `pg_dump` الرسمي. تستخدم إعداد اتصال للقراءة فقط، ولا تصدر صفوف الجداول أو كلمات مرور أدوار PostgreSQL. تحتاج PGHOST وPGDATABASE وPGUSER وإعداد اعتماد خاص مثل PGPASSFILE؛ لا تدخل كلمة المرور في الأمر. للاتصال البعيد يلزم PGSSLMODE=verify-full وشهادة موثوقة. لا تحول اتصالاً غير صالح إلى SSL غير متحقق لتجاوز الخطأ.

```bash
node scripts/export-schema.mjs /private/zoer-schema-new your_actual_schema
```

المجلد الأب يجب أن يكون موجوداً، ومجلد النتيجة جديداً وخارج المستودع. تنشئ الأداة `database-schema.sql` و`export-report.json` بصلاحيات 0600 داخل مجلد 0700، مع SHA-256 وتوقيت الاستخراج. تمنع استبدال تصدير سابق وتمسح مخرجاتها الجزئية عند الفشل. لا تطبع تشخيص قاعدة البيانات أو الاعتماد. `pg_dump` يجب أن يكون متوافقاً مع إصدار الخادم.

يشمل التصدير schema المحدد فقط؛ راجع اعتماداته على schemas أخرى والامتدادات. تعاريف الدوال والقيم الافتراضية قد تحتوي أسراراً تاريخية، لذلك يبقى التصدير خاصاً حتى دون صفوف. نجاح الاستخراج لا يثبت قبول التطبيق أو الاستعادة أو الامتثال القانوني. إذا لم يوفر Zoer اتصالاً مباشراً، يلزم تصدير مخطط من المزود؛ إنشاء migrations جديدة لا يعوّض عنه.

الأداة تحول ملف JSON الأصلي إلى SQL قابل للاستيراد في PostgreSQL، داخل **schema جديد ومعزول**. ملف البنية الذي أعطاه Zoer لم يتضمن تعريفات صحيحة للجداول؛ لذلك نستعمل `schema/reconstructed-staging.sql` المبني من الأعمدة الملاحظة سابقاً. هذه ليست شهادة بأن أنواع الأعمدة والقيود والفهارس مطابقة لقاعدة الإنتاج.

## التحويل دون اتصال بقاعدة بيانات

تحتاج Node.js 22 أو أحدث. احفظ المصدر والمخرجات في مجلد خاص خارج مستودع Git. لا ترفع ملفات قاعدة البيانات إلى GitHub أو إلى رابط عام.

```bash
node scripts/convert-database.mjs /private/export.json /private/jd-staging.sql jouw_driver_staging
```

ينشئ ملف SQL وتقرير `jd-staging.sql.report.json` بصلاحيات `0600`، ويرفض استبدال ملف موجود. يجب أن يكون مجلد `/private` خاصاً بالمستخدم أيضاً، والمجلد مجرد مثال. ملف SQL يحتوي معلومات شخصية وتجارية؛ التقرير يحتوي أسماء جداول وأعمدة وأعداداً فقط.

الأداة:

- تقبل الجداول والأعمدة المعروفة في ملف البنية فقط؛ ترفض الأسماء الغريبة والأنواع غير المطابقة والمعرفات المكررة.
- تقرأ أرقام JSON دون تقريب JavaScript، بما فيها BIGINT والأرقام المالية وداخل JSONB.
- تحافظ على النصوص، والقيم `NULL`، والطوابع الزمنية مع المنطقة الزمنية، وتعيد ضبط تسلسل المعرفات بعد الاستيراد.
- تُنشئ البنية والصفوف في transaction واحد. `CREATE SCHEMA` يفشل إذا كان schema موجوداً، فيمنع الدمج في بيانات سابقة. لا توجد أوامر حذف أو استبدال للجداول.
- تدرج القيم بإفلات ثابت مع `standard_conforming_strings=on`؛ لا تُنفذ أوامر SQL من ملف التصدير.
- تسجل عدد المراجع المحتمل فقدانها حسب أسماء الأعمدة المعتادة، من دون طباعة معرفات أشخاص أو حذف سجلاتهم. هذا فحص استدلالي، وليس بديلاً عن القيود الأصلية المفقودة.

## بيانات المصادقة والتكامل

لا تُستعاد الجلسات القديمة ولا رموز الدخول: تُترك `sessions` و`refresh_tokens` و`distributor_sessions` و`user_oauth_providers` و`user_passcode` فارغة. وتُترك `chiron_tokens` و`chiron_settings` و`chiron_api_config` و`chiron_oauth_log` فارغة، لتجنب إعادة تشغيل تكامل أو رمز قديم.

تُمسح أعمدة كلمات المرور وهاشاتها وأسرار العملاء ورموز الجلسة المعروفة في الجداول الأخرى. تظهر أعداد الاستبعاد والمسح في التقرير. لهذا **لا يمكن تسجيل الدخول بحسابات الإنتاج بعد هذا الاستيراد** قبل إعداد عملية استعادة الحسابات أو حسابات اختبار جديدة منفصلة. إعداد Chiron يتم من جديد بالأسرار المشفرة وإعدادات الخادم المقبولة، ثم اختبار القبول لدى المزود. لا تنشر هذه النسخة على الإنترنت بمجرد استيرادها.

الملفات تظل حساسة حتى بعد مسح حقول الاعتماد: السجلات والنصوص الحرة قد تحتوي معلومات سرية غير منتظمة. تعامل معها كنسخة خاصة ولا تعتبر الأداة بديلاً عن مراجعة البيانات والأسرار قبل أي نقل خارجي.

## استيراد اختياري في قاعدة اختبار محلية منفصلة

تحتاج أداة PostgreSQL `psql`. جهّز قاعدة فارغة منفصلة، باسم يتضمن `staging` أو `sandbox` أو `test`، ومستخدم مخصص يملك صلاحية إنشاء schema فيها. استخدم ملف اعتماد PostgreSQL خاصاً `PGPASSFILE` بصلاحيات `0600` أو المصادقة المحلية؛ لا تكتب كلمات مرور في سطر الأوامر أو Git.

```bash
export PGHOST=127.0.0.1
export PGPORT=5432
export PGDATABASE=jouw_driver_staging
export PGUSER=staging_importer
export PGPASSFILE=/private/pgpass
export STAGING_IMPORT_ACK=empty-isolated-staging
node scripts/import-staging.mjs /private/export.json jouw_driver_staging
```

سكربت الاستيراد يعيد بناء SQL من JSON بنفسه، ولا يستقبل ملف SQL عشوائياً. يرفض `NODE_ENV=production` وغياب اسم قاعدة اختبار صريح. عند فشل أي أمر يلغي transaction؛ يعرض رسالة مختصرة دون تفاصيل السجلات. هذه الحواجز لا تتحقق من كل سياسات الاستضافة: تأكد عملياً أن الاتصال بقاعدة الاختبار المنفصلة قبل تشغيله. لا يُستخدم على قاعدة Zoer الحية.

## التحقق المنفذ

اختبارات المحول موجودة في `tests/database-conversion.test.mjs` وتشمل دقة المعرفات، والهروب من النصوص، ورفض الأعمدة والجداول الغريبة، والأنواع، واستبعاد الجلسات، وصلاحيات الملفات.

```bash
node --test tests/database-conversion.test.mjs
```

نتائج معالجة البيانات المستوردة وتقارير أعدادها وروابطها تبقى خاصة خارج المستودع العام. اختبارات المحول الاصطناعية تتحقق من الدقة والهروب والأنواع والاستبعاد والصلاحيات؛ قبول بيانات التشغيل يحتاج مراجعة مستقلة وفق العقد الجديد. لا تحذف الأداة سجلات الأعمال أو تصلحها تلقائياً.
