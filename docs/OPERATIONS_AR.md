# تشغيل إصدار مستقل بواسطة GitHub

GitHub يحفظ المصدر ويشغّل فحوص Actions ويبني صورة GHCR. قاعدة PostgreSQL والخادم يعملان على خادم Linux مملوك للشركة؛ GitHub Pages لا يشغّل هذا التطبيق أو قاعدة بياناته.

## تجهيز الخادم مرة واحدة

1. جهّز خادم Linux مع Docker Engine وCompose حديث يدعم `--wait`، وNode 22.18+ وage، ودومين يشير إليه. افتح 80 و443 وقيد SSH. حساب النشر عضو مجموعة Docker؛ هذه صلاحية قوية، فخصص مفتاحاً لهذا المشروع وحده.
2. أنشئ `/srv/jouw-driver` و`releases` و`backups` بصلاحيات 700 ولحساب النشر. ضع إعدادات `deploy/.env.example` في `/srv/jouw-driver/.env` بصلاحيات 600، وأضف `BACKUP_RECIPIENT` العام. احتفظ بالمفتاح الخاص خارج الخادم. لا تستخدم حسابات التجربة.
3. استورد البيانات في قاعدة منفصلة وراجع العلاقات ثم اعتمد المخطط وفق دليل قاعدة البيانات المستقلة. أداة النشر تطبق ترحيلات الإصدار؛ لا تنشئ بيانات العمل ولا تختار هويات للسجلات المفقودة.
4. اضبط PostgreSQL وPostgREST بإصدارات مختبرة. سجّل دخول GHCR على الخادم إذا كانت الحزمة خاصة باستخدام token قراءة packages فقط؛ لا تنقل هذا token إلى التطبيق. حافظ على نفس اسم Compose `jouw-driver` حتى لا تنشأ وحدات تخزين مختلفة.
5. أنشئ بيئتَي GitHub `staging` و`production`. قيد فروعهما وأضف required reviewers للإنتاج حين تسمح خطة GitHub. لكل بيئة أسرار `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`. القيمة الأخيرة هي مفتاح المضيف الذي تم التحقق من بصمته خارج الاتصال الأول؛ لا تستخدم ssh-keyscan لتوثيق مضيف مجهول تلقائياً. استخدم خادمين منفصلين للتجربة والإنتاج.

## إصدار ونشر

شغّل **Verified server image** على الفرع أو وسم إصدار. يجب نجاح فحوص التطبيق وقاعدة PostgreSQL الأصلية قبل نشر الصورة. ملخص التشغيل يعطي مرجع GHCR مع digest وcommit SHA. هذه الصور ثابتة بالdigest، ولا يستخدم النشر latest.

شغّل **Deploy verified server image** وأدخل المرجع والـSHA وبيئة staging. أداة الخادم تطابق وسم revision داخل الصورة مع ترحيلات نفس commit، تفحص إعدادات التشغيل، تسحب الصورة، تنتظر القاعدة، وتنشئ نسخة مشفرة قبل إيقاف الواجهة وتطبيق الترحيلات. ثم تعيد PostgREST والتطبيق وتفحص HTTPS. توجد فترة توقف أثناء الترحيلات؛ هذا المسار ليس نشرًا بلا توقف.

بعد قبول الحسابات والرحلات والفواتير وPDF وعزل الشركات والهاتف وChiron، جهّز بيئة production وبياناتها واعتماد قيودها ثم شغّل نفس الـdigest. رفض الإنتاج عند عدم اعتماد المخطط مقصود. كِلا البيئتين تحتاج BACKUP_RECIPIENT لأن النسخ قبل الترحيل إلزامي.

## مراقبة وتعافٍ

- راقب HTTP، وصحة حاويات التطبيق والقاعدة، ومساحة القرص، وأخطاء الخادم. تحقق من سلامة TLS والبريد وقبول Chiron بصورة مستقلة عن نجاح البناء.
- جدولة النسخ خارج GitHub: شغّل `backup.sh` من مجلد الإصدار مع COMPOSE_PROJECT_NAME=jouw-driver وCOMPOSE_FILE لمسار compose المطلق وBACKUP_RECIPIENT. خزّن النسخ خارج الخادم واختبر استعادة قاعدة معزولة دورياً. مثال تحميل env دون تنفيذ نص الملف: `node --env-file=/srv/jouw-driver/.env --input-type=module -e 'import {spawnSync} from "node:child_process"; process.exit(spawnSync("sh",["backup.sh"],{stdio:"inherit"}).status ?? 1)'` من deploy بعد تعريف متغيرات Compose. لا تطبع config المحلول لأن فيه أسراراً.
- إذا فشلت الترحيلات تبقى الواجهة متوقفة؛ راجعها على staging وأصلحها للأمام. لا يحاول المسار إعادة قاعدة الإنتاج تلقائياً. ملف release.json يوثق آخر إصدار نجح، وprevious-release.json يوثق سابقه.
- الرجوع للصورة السابقة ممكن فقط إذا ثبت توافق مخطط البيانات الحالي معها. اجعل APP_IMAGE هو digest السابق، ثم Compose up باستخدام ملفات الإصدار المعني ونفس المشروع والبيئة. البيانات التي أُنشئت بعد النشر لا تُستعاد فوقها نسخة قديمة بصورة تلقائية.
- تعافي كامل: قاعدة جديدة معزولة، استعادة age وpg_restore والأدوار ومفاتيح التطبيق، مطابقة السجلات والتسلسلات، إبطال الجلسات، ثم تحويل النطاق بعد اختبار القبول. نسخة قاعدة واحدة لا تحتوي مفاتيح تشفير التطبيق وكلمات مرور الأدوار.
- قفل `.deployment-lock` يمنع نشرين بالتوازي على المضيف. إذا انتهت العملية بصورة مفاجئة، تحقق أنه لا يوجد نشر يعمل قبل حذف القفل يدوياً.

## حدود التسليم

الكود ووصفات البناء والنشر موجودة في GitHub. لا توجد هنا بيانات اتصال لخادم الشركة أو DNS أو أسرار GHCR خاصة أو مفاتيح توقيع الهواتف. إنشاء workflows لا يعني أن النسخة الحية نشرت، أو أن التطبيق اجتاز قبول خلفية الهاتف وChiron. هذه الخطوات تُثبت على البيئة الفعلية قبل دعوة العملاء.
