# قاعدة PostgreSQL مستقلة لـJOUW DRIVER

اعتمدنا مسار قاعدة مستقلة يملكها المشروع؛ لا نحتاج مطابقة Zoer حرفياً أو انتظار تصدير مخططه. `schema/reconstructed-staging.sql` هو أساس الجداول المتوافقة مع الأعمدة المتوفرة، و`schema/independent-contract.json` يحدد قواعد النسخة الجديدة. هذا اعتماد لمسار التطوير، وليس تصريحاً بتشغيل البيانات المستوردة قبل مراجعتها.

## قواعد النسخة الأولى

- 14 علاقة أساسية بين الشركات والحسابات والسائقين والسيارات والرحلات والفواتير.
- ارتباط سائق الرحلة وسيارتها بشركة الرحلة؛ دون مساواة حساب صاحب السجل بحساب السائق الحالي. قد يكون منشئ السجل مديراً أو يكون ارتباط السائق بالحساب تغير لاحقاً. صلاحيات التطبيق والتحقق من السائق في الرحلات الجديدة تبقى منفصلة عن معنى السجل التاريخي.
- حدود إحداثيات الموقع، وقيم الرحلة غير السالبة، وترتيب وقت البداية والنهاية، ووجود الهوية والتوقيت للرحلة المكتملة.
- العلاقات لا تستخدم ON DELETE CASCADE؛ حذف المرجع المستخدم يُرفض.

تُضاف القيود أولاً بوضع NOT VALID: تُحفظ السجلات القديمة كما هي، وتُمنع المخالفات الجديدة. تعديل سجل قديم مخالف قد يُرفض؛ لا نقدم هذا الوضع كتشغيل إنتاج مقبول. أداة التحقق لا تحذف سجلات ولا تنشئ حسابات أو سيارات وهمية لتجاوز القيود. VALIDATE CONSTRAINT لا ينجح حتى تُراجع الحالات القديمة أو تُعتمد خطة أرشفة منفصلة تحفظها.

## تشغيل أدوات المشروع على قاعدة منفصلة

1. استورد التصدير المحوّل في schema اختبار فارغ، وفق `DATABASE_IMPORT_AR.md`. لا تنفذ SQL التاريخي لـZoer مباشرة.
2. من deploy، اضبط SCHEMA_SOURCE=independent وDEPLOYMENT_MODE=staging وSCHEMA_VALIDATED=false، ثم طبّق الإصدار باستخدام `node --env-file=.env ../scripts/apply-release.mjs`. تنشئ هذه الخطوة قواعد العقد الأساسي بعد ترحيلات الأمان. لا تغير قاعدة Zoer الحالية.
3. عند وجود اتصال مباشر للقاعدة الجديدة، شغّل `node scripts/audit-independent.mjs /private/new-audit.json your_schema`. تحتاج PGHOST وPGDATABASE وPGUSER واعتماداً خاصاً؛ للاتصال البعيد PGSSLMODE=verify-full. الأداة للقراءة فقط، وتنتج أعداداً دون أسماء أشخاص أو معرفاتهم، بصلاحية 0600 خارج Git. رمز الخروج 2 يعني وجود مخالفات، وليس نجاح القبول.
4. راجع المراجع المفقودة والارتباطات التاريخية بإجراء موثّق، أو صمّم أرشيفاً منفصلاً قبل نقلها. احتفظ بمعرفاتها وقيمها المالية ومصدرها؛ لا تعيّن سائقاً أو سيارة تخميناً. لا تغيّر قاعدة الإنتاج لإصلاح نسخة الاختبار.
5. بعد نجاح التدقيق والمراجعة، اضبط INDEPENDENT_SCHEMA_VALIDATE=true وأعد خطوة تطبيق الإصدار. التحقق يجري في transaction؛ الفشل لا يحذف السجلات ولا يُعلن نجاح القبول.

بوابة إنتاج مستقلة تتطلب SCHEMA_SOURCE=independent وSCHEMA_VALIDATED=true، ويستدعي فحص الإقلاع independent_schema_ready عبر PostgREST. يرفض الإقلاع إذا كانت إحدى القيود الأساسية مفقودة أو غير معتمدة؛ العلم البيئي وحده لا يكفي. تبقى مراجعة بقية الوظائف والفواتير والاحتفاظ والنسخ والمفاتيح والهاتف وChiron لازمة.

## حدود القبول

تقارير البيانات المستوردة ونتائج تدقيقها تُحفظ في ملفات خاصة خارج GitHub. لا ترفع سجلات العملاء أو أعدادها أو تفاصيل الربط المستخرجة منها إلى المستودع العام. مراجعة المراجع التاريخية وقبول البيانات الفعلية واستعادة الحسابات تبقى إجراءات مستقلة.

اختبارات PostgreSQL الأصلي في CI تستخدم بيانات اصطناعية، وتتحقق من العلاقات والقواعد وبوابة الإقلاع إلى جانب المصادقة والرحلات والاستعادة المشفرة. الدليل المعتمد ومعرف الكود في tests/verification/github-actions.json؛ لا تُنسب نتيجة تشغيل سابق لتعديل جديد.
