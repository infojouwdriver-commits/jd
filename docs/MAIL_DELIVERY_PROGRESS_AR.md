# متابعة إصلاح البريد — دفعة قابلة للمراجعة

الفرع `feat/transactional-mail-review` مستقل عن الدفعات المنشورة. هذه الدفعة لم تُدمج أو تُنشر، ولم تُرسل رسالة حقيقية أثناء الاختبار.

- خدمة إرسال معاملات عبر Resend الموجود في المشروع. يتوقف الإرسال دون مرسل ونطاق موثق وتأكيد الخطة المجانية ومفتاح ثابت لبصمات البيانات.
- حصة خادم 90 طلباً يومياً و2700 شهرياً؛ تحتسب الطلبات غير المؤكدة أيضاً. قفل قاعدة البيانات يمنع تجاوز الحصة وتزامن تسجيل الرد وأحداث التسليم.
- تحفظ بصمات مرتبطة بمفتاح تشفير ثابت ومعرّف المزود والحالة، دون عناوين المستلمين أو نصوص الرسائل أو رموز التحقق.
- مفاتيح حدث ثابتة وحجز واحد يمنعان إعادة إرسال حدث حُجز أو بقي مصيره غير مؤكد. القبول لدى المزود ليس تسليماً مثبتاً.
- أحداث التسليم والارتداد والشكوى لا تتكرر ولا تخفض حالة تسليم مثبتة، ويُراجع الحدث الذي يصل قبل تسجيل رد المزود عند إكمال التسجيل.
- أصبح إرسال رمز التحقق يستخدم خدمة المعاملات والحجز الذري بدلاً من الاستدعاء المباشر للمزود. لا تدّعي الواجهة نجاحاً عندما تكون الإعدادات ناقصة أو يرفض المزود الطلب.
- أضيف endpoint لأحداث Resend يتحقق من توقيع Svix على النص الخام قبل تحليل الحدث، ثم يسجل الحدث بمعرفه الفريد. الأحداث غير المؤثرة مثل الفتح والنقر لا تتحول إلى إثبات تسليم.
- أضيف ترحيل البريد إلى اختبار المكدس ومسار الإصدار والنشر الإضافي، وأضيفت متغيرات الإعداد بصورة تفشل مغلقة افتراضياً.
- نجح فحص الأنواع والبناء الإنتاجي و15 اختباراً مركزاً واختبارا قاعدة البيانات المعزولة. يبقى CI ومراجعة طلب الدمج والقبول الأصلي لـPostgreSQL/PostgREST قبل الدمج أو النشر.
- مراجعة حساب المزود المتصل لم تجد نطاق إرسال مضافاً؛ اختبار التسليم الحقيقي يحتاج نطاقاً يملك المشروع صلاحية DNS له وإعداد الخدمة. عنوان المرسل التجريبي الافتراضي لا يحقق ذلك.

المراجع الرسمية: https://resend.com/pricing?product=transactional وhttps://resend.com/docs/webhooks/verify-webhooks-requests وhttps://resend.com/docs/dashboard/emails/idempotency-keys . لم يُفعّل تجاوز مدفوع للحصة أو تتبع الفتح والنقر.

التسليم الحقيقي غير مثبت حتى يُضاف نطاق موثق ومفتاح webhook ومرسل معتمد ومستلم اختبار مأذون، ثم يصل حدث `email.delivered` الموقّع. قبول API وحده لا يكفي.
